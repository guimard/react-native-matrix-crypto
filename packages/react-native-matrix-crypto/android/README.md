# android/

Mostly generated by `uniffi-bindgen-react-native` (`yarn codegen`) — see
`scripts/assert-no-drift.sh` at the repo root, and never hand-edit those files.

## Why `src/main/jniLibs/*/libmatrix_crypto_ffi.a` ships (~66 MB, three ABIs)

`package.json`'s `"files"` allowlist names `android/src/main` explicitly, which ships
the prebuilt per-ABI Rust static libraries under `jniLibs/` along with the real source
(`AndroidManifest.xml`, the Kotlin module classes). Those `.a` files are large —
roughly 20-24 MB each for `arm64-v8a`, `armeabi-v7a`, and `x86_64` — and it is tempting
to read that as bloat and trim it. Do not: it is load-bearing, not incidental.

`CMakeLists.txt` (generated, in this same directory) imports whichever one matches the
ABI being built as a static library —

```cmake
add_library(my_rust_lib STATIC IMPORTED)
set_target_properties(my_rust_lib PROPERTIES IMPORTED_LOCATION ${MY_RUST_LIB})
```

— and links it into this module's own `.so`. That is what lets a consuming app
autolink and build `react-native-matrix-crypto` from source, the standard way React
Native Android libraries are consumed, **without needing a Rust toolchain, cargo-ndk,
or the Android NDK's Rust target support installed at all** — only the prebuilt `.a`
and a normal C++/NDK build. Drop `jniLibs` from what ships and every real Android
consumer's own `./gradlew` build breaks the moment it reaches
`configureCMakeDebug[<abi>]`/`configureCMakeRelease[<abi>]`, with no local symptom in
this repository to catch it first (Task 11's iOS gap and this are the same class of
defect, in opposite directions: there, a binary that should have shipped didn't; here,
a binary that must keep shipping could quietly stop).

A root-level `*.aar` used to ship too, as a separate, additional convenience artifact —
a fully prebuilt, already-linked module for a consumer who would rather not build from
source at all. It never replaced `jniLibs`, and nothing ever autolinked against it
automatically; it was dropped from `package.json`'s `"files"` in the M2 cleanup (root
README, Installation section) because that consumer had no mechanism to reach it.
